结构体检报告 · 人读版

对象：「跨平台外挂监管种子」工具包（Apache-2.0 开源，实验性参考实现）· 体检日期 2026-10-04 · 体检人：钥匙（跨领域结构分析专家）

结论一句话：
这份东西的设计思路是干净的、甚至比多数同类项目更讲究；问题出在——它把"这套监管是不可被别人改掉的"这句话，交给了一条自己也能随时改掉的锁去保证。所以它现在能"看着"，但还不能真的拦人。

大白话补充：他不是设计错了，是"说了十分、做到了六分"，其中最关键的那一分（拦得住）还在说明书的承诺里，没落到机器里。

一、一分钟读完

做对了什么："只观察、只建议，不越权去拦"这个分寸感做得非常好——默认不拦人，要拦必须有人正式授权，而且授权不全时它会自己退回"只建议"。这是很多同类工具最缺的克制。
出了什么问题：三道最要紧的安全承诺——"规章改不了""改了会被发现就不动手""能喊停"——第一道锁的钥匙和被锁的东西放在同一个抽屉里；第二道在执行时走错了路（被改了不是拦住，是放行）；第三道的哨子根本不会响。
最该警惕的陷阱：说明书里的"最小运行示例"是自己先报了身份的示范用例，所以看起来"已经拦住了"。真实环境里没人替它报身份，两条最关键的规则（沙盒越狱、偷数据外发）实际上一次都不会触发——这会给使用者一种"我已经被保护了"的错觉。

二、它到底是干什么的

生活类比：它相当于在 AI 助手的"手"前面，请了一位第三方保安。AI 每要做一个动作（删文件、发网络请求、跑命令），先过一遍保安手里的《禁令清单》：清单上没写 → 放行；写了 → 记一笔（观察）、或者提醒你一句（建议）、或者直接按住不让做（制止）。

输入 → 输出：输入是"AI 准备做的一个动作"，输出是一个判定结果：观察 / 建议 / 制止 / 放行。它不改 AI 本体，随时可以拆掉——这就是它最想强调的"外挂优于内改"。

这份"体检"只判断：它的机构设置、岗位职责、规则条文之间是否讲得通、有没有互相打架、有没有该有人管的环节没人管。它管不管用（漏报多少、误报多少）不在这份报告的能力范围内——那要在真实活儿里跑数据才算得出来。

三、结构体检：四个最反直觉的地方

下面四条都是**现场实测**出来的（在隔离环境里真跑了一遍，不是读文档猜的）。左边是它对外宣称的强度，右边是实测到的强度。

① 防篡改：宣称"谁改都能发现"　vs　实测"改完顺手把印章也重盖一遍就查不出来"

② 篡改应对：宣称"发现被改就降级"　vs　实测"被改后直接放行"

③ 制止能力：宣称"退出码 2 硬阻断"　vs　实测"程序永远以 0 结束，哨子不响"

④ 规则覆盖：宣称"7 条越界规则"　vs　实测"2 条活在没人负责的标签上，官方示例里那一栏是空的"

这几条恰恰说明一件事：会写安全文档 ≠ 能免疫自己的安全盲区。这个项目在文档里反复强调"不伪成功、不虚假监管"——这个态度是对的，但同样的标准还没有回头照到它自己的代码上。

四、必须马上修的 4 件事

P0-1｜锁和钥匙放在同一个抽屉里

怎么讲：它为了证明"规章没被人动过"，给规章配了一个"指纹印章"。可这个印章是"算出来的"——任何能改规章的人，都能顺手把新规章再算一遍指纹盖上去。于是"改过"这件事就查不出来了。实测：改完规章、重算印章，系统照样报"完好"。

怎么改印章换成"必须有一把外部密钥才能盖"的形式，这把密钥不出现在被监管的那台环境里；实在来不及，就至少把印章放在被监管方"只能读、不能写"的位置，并在说明书里老实写清"现在这个指纹只是查一致性，算不上防篡改"。
修完怎么确认手动改规章 + 重新盖一遍印章，系统必须报"不可信"。现在是报"完好"——所以这条现在没通过。
P0-2｜被改了不是拦住，而是放行

怎么讲：像小区门口立着"禁止入内"的牌子，牌子上还写着一行小字："如果发现牌子被改过，保安就不许动手拦人。" 那想进去的人会怎么做？——把"禁止入内"那几个字擦掉。牌子被改过 → 保安不许拦 → 而且清单上没有可拦的条目 → 直接放行。实测确实如此：篡改后的结果是放行，只在角落里打了一行提示。

怎么改把"规章不可信"提升为全局开关：只要发现规章被动过（或读不出来），所有判定一律不许出"放行"，全部转人工复核。原来的"默认不拦"要保留，但"不可信时绝不放行"要新加上。
修完怎么确认篡改后再跑一次，结果不得是"放行"。现在是放行——没通过。
P0-3｜说明书写"吹两声哨子就停"，但这只哨子不响

怎么讲：接入说明里写着"制止档：程序会以错误码 2 结束，宿主看到就阻断"。可这个程序从第一行到最后一行的代码，永远以 0（正常）结束。也就是说，如果有人照着说明书接线，那个"硬阻断"永远不会发生。

这一条要先跟你确认：到底是"程序负责吹哨"（那就是代码缺了这段），还是"接线的人自己看判定结果再决定"（那就是说明书这句话写错了）。两种改法都简单，但不能都不做。

怎么改二选一：给程序加"判定为制止时以错误码 2 结束"；或者把说明书改成"接线的人读到判定结果后自己阻断"，并附一段接线示例。
修完怎么确认实测一次"制止"场景，看错误码是不是 2（现在是 0）。
P0-4｜两条最关键的规则，要求"坏人自己先报名"

怎么讲：7 条规则里，"沙盒越狱"和"未授权往外发数据"这两条最要紧的，判断方式不是看动作本身，而是看动作上有没有贴一个"我是越界行为"的标签。而官方给的接线示例里，这一栏填的是空。没人负责贴标签 → 这两条规则永远不触发。更麻烦的是：说明书的运行示例用的是已经贴好标签的示范数据，所以看起来是有效的。

怎么改给这两条补上"看动作本身"的兜底关键字（比如 mount --bind、unshare 这类越狱特征）；再在接线自查清单里明确写上"标签由谁负责贴、贴漏了怎么办"；说明书补一组"没贴标签"的用例，把真实结果写出来。不要靠加一大堆宽泛关键字硬凑——那会把误报率推高，反而毁掉默认开着的"建议"档。
修完怎么确认模拟一次"没贴标签"的越狱动作，结果不得是"放行"。现在实测是放行——没通过。

五、千万别改的东西

这几处是刻意设计，不是毛病。动了会伤到根子：

  1. 三档默认值（只观察、只建议默认开，制止默认关）。这是"没授权就不越权动手"的落点。
  2. 降级而不是放行。命中高危但没授权时退回"建议"并写明理由。千万别为了"看起来更安全"改成默认拦截（那就是越权），也别改成默认放行（那就是虚假监管）。
  3. 判定只写一份。四个平台共用同一个判定内核，这是它最值钱的结构选择，不要为图方便在每个平台各写一份。
  4. "提示词注入"那条规则不制止。它是中危，配套行为就是"不拦"，前后是自洽的——别因为"看起来不一致"就改成拦。
  5. 授权四项只是"填没填"的检查。作者自己已经诚实标注过"声明不等于验证"。要提升强度请走 P0-1 那把外部钥匙，别在核心里做一个假的"强验证"——那比现在更糟。
  6. 企业级的容器/系统级加固"只给配置、不在本机验证"。这是正确的自我约束（那部分必须在真实 Linux 主机上验）。不要为了好看伪造一个"已通过"。
  7. 英文目录名（adapters / deploy / docs / examples / kernel）不是缺陷。顺便说明一下：你发我的那张截图里显示的"适配器/部署/纪录片/示例/内核"是浏览器自动翻译的显示效果，仓库里真实的目录名是英文的，docs 被翻译成了"纪录片"——这不是仓库的问题，我不会把它算成缺陷。
  8. "装完就能用"的低摩擦入口要保留。别为了安全叙事把默认态收紧成"没授权就完全不能用"。

七、下一步

  1. 先回答一个判断题：P0-3 里"哨子由谁吹"（程序吹 / 接线人自己阻断），定了才好动代码。
  2. 再答一个选择题：防篡改那把外部钥匙放在哪？（这是 P0-1 的前提，也直接关系到"监管方要有自己的凭据"这条边界的取舍。）
  3. 然后按顺序做：P0-1 与 P0-2 必须同一批做（只做一条，另一条还是直通路径）→ P0-4（补兜底关键字）→ P0-3 → 再进 P1。
  4. 每改完一条，跑一次实测，不要凭"代码已改"就算完成。人读版和机读版里，每条都写了"修完怎么确认"。

如果只做一件事：做 P0-2。因为它把"监管失效"从"能被发现"变成了"悄无声息"，而这一条恰好是七行代码就能挡住的口子。

九、哪些话不能全信

  • "能拦住"这件事，还没在真实平台上验过。本项目自己说四个平台"尚未全量实测"，本报告也只在本机跑了判定逻辑，没在真实宿主里验证"拦得住"。
  • 规则好不好用（漏报多少、误报多少），本报告算不出来。那需要在真实任务上跑一批带标准答案的样本。所以别把"7 条规则"理解成"覆盖了 7 类风险"。
  • 容器/系统级加固那部分，本报告没验。必须在真实 Linux 主机和真实集群上跑才算数。
  • "监管服务谁都能调"是否可以接受，取决于你的真实网络和调用方——这一点需要你给信任模型，我不替你定。
  • 能不能满足比赛/评审的口径（命名、正式版本、文档完备度），需要评审细则原文，本报告不判。
  • 本报告里凡是写"实测"的结论，都是 2026-10-04 在隔离目录实跑出来的；写"静态分析"的，是读配置与代码推出来的，没有跑。两类已分别标注。
